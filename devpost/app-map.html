How Porchlight fits together

Porchlight gives each person in a family their own homepage, and every widget on it is AI-driven. You type a sentence like “show me upcoming SpaceX launches” and a live widget appears. Articles and local events pick themselves from your interests.

The main pieces

React frontend

frontend/src. The pages, the widget cards, Arrange mode (Puck), and the family sidebar. It only talks to the Go API.

Go API

backend/. Routes, sessions, the widget pipeline, and every call to the outside world. Your API keys stay here.

SQLite

backend/porchlight.db. Accounts, families, invites, profiles, saved widgets and page layouts. The schema is in backend/migrations/.

OpenRouter + Brave

The LLM chooses what to search for and shapes the results. Brave Search supplies the live data.

One action, end to end: “describe a widget”

What happens between pressing Enter in the + prompt and a new card appearing:

  1. You type a sentence and press Enter frontend/src/widgets/DescribeWidgetPrompt.tsx → useCreateWidgetFromPrompt in frontend/src/api/hooks.ts sends POST /api/widgets/from-prompt
  2. The Go router matches the request and checks you’re logged in backend/routes.go → routes(), the line mux.Handle("POST /api/widgets/from-prompt", private(...))
  3. The LLM plans the widget: title, data source, search query, display shape backend/internal/widgets/handler.go → FromPrompt calls PickWidgetSpec (backend/internal/llm/spec.go) OpenRouter
  4. Brave Search fetches live results src.Search, via the registry in backend/internal/sources/ Brave Search
  5. The LLM shapes the results into items, and then Go checks them ShapeItems → groundItems and before in backend/internal/llm/items.go: made-up links are blanked, past dates dropped, repeated text removed OpenRouter
  6. The widget is saved and added to the end of your layout CreateCustomWidget (backend/internal/store/widgets.go) and AddCustomWidget (backend/internal/layout/handler.go) SQLite
  7. The card appears with the amber “fresh” border frontend/src/puck/LayoutView.tsx → WidgetCard (frontend/src/widgets/WidgetCard.tsx) and one of the renderers in frontend/src/widgets/renderers/

The Go route you walked

You followed these three stops during the wrap-up. Search for the anchor in your editor rather than relying on line numbers.

1 · The router and its middleware

backend/routes.go · search “POST /api/widgets/from-prompt”

Go 1.22’s standard http.ServeMux matches the method and the path in one pattern. A middleware is a function that takes a handler and returns a new one. private(h) wraps h in RequireAuth, so the handler only runs for a logged-in person.

mux.Handle("POST /api/widgets/from-prompt", private(widgetHandler.FromPrompt))

2 · The kernel handler and the interface it declares

backend/internal/widgets/handler.go · FromPrompt, type Planner interface

FromPrompt runs the kernel in four steps: decodePrompt, then PickWidgetSpec, then src.Search, then ShapeItems. Errors are mapped to clear HTTP statuses: 422 when the LLM can’t pick a source, 502 when an outside service fails.

type Planner interface is declared by the code that uses it. *llm.Client satisfies it without ever naming it. That’s why TestFromPrompt (handler_test.go) can pass in a fake planner and never touch the network.

3 · Go checks the model’s answer

backend/internal/llm/items.go · groundItems, before

After the LLM answers, groundItems blanks any URL that wasn’t in the search results. When the request is about upcoming things, before drops items dated before today. The model only supplies a machine-readable sort_date; Go makes the comparison.

// Both sides are YYYY-MM-DD, so comparing the strings compares the dates.
return d.Format(time.DateOnly) < cutoff

This is pinned by the test case "future_only drops items dated before today" in backend/internal/llm/llm_test.go.

A practice to reuse

Let the model suggest; let code decide, and pin it with a test

What happened: after slice 1, the SpaceX widget kept listing launches that had already flown, even though the prompt gave the model today’s date. Rewording the prompt didn’t make it reliable.

What fixed it: the model now returns a plain sort_date and a future_only flag, and Go’s before does the date comparison (backend/internal/llm/items.go). A table-test case in llm_test.go uses dates relative to today. Live runs then returned only upcoming launches, five times out of five. The same idea guards links (groundItems) and repeated text (the Quote of the Day fix).

Use it again: on any backend that takes LLM output — dates, IDs, URLs, numbers, permissions — ask the model for structured data, then make the decision in your own code with a small table-driven test. A related lesson from your wrap-up edit: when the same text or rule lives in two places (Go title and frontend heading), a test on one copy won’t catch the other. Keep one source of truth, or test both.
