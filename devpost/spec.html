Devpost Learn — Technical Spec

Porchlight

A Go API + React SPA, with Puck for the canvas and OpenRouter as the LLM proxy. Server-mediated LLM calls, SQLite for storage, and a constrained free-form render spec from the LLM as the kernel.

How This Works, In Plain Language

Two halves that talk JSON over HTTP

The Go backend is a single program on your computer. It owns the database (a small SQLite file), handles logins, and is the only thing that talks to the LLM (via OpenRouter) and to Brave Search. It speaks JSON over a REST API.

The React frontend is a single-page app in a browser. It uses Puck to render and edit the homepage canvas, and TanStack Query to fetch data from the Go API. The user logs in, the React app asks the Go API for the family's data, and Puck renders the homepage using the user's saved layout.

The kernel — "describe a widget" — the user clicks "+" in Puck, types a sentence, the React app POSTs that sentence to the Go API, the Go API calls OpenRouter with a structured-output prompt, the LLM returns a small JSON spec (which data source, what to search for, and how to render the result), the Go API calls Brave Search to fetch the data, persists the new widget, and returns the rendered spec. Puck adds the new widget to the page. The OpenRouter key stays on the server.

Go backend :8080

  • net/http ServeMux (Go 1.22+ patterns)
  • alexedwards/scs/v2 sessions (SQLite-backed, httpOnly cookies)
  • modernc.org/sqlite (pure Go, no CGO)
  • sashabaranov/go-openai → OpenRouter
  • Brave Search HTTP adapter
  • Source registry (interface-driven; v2 can add sources)

React SPA :5173

  • React 18 + TypeScript + Vite
  • TanStack Router (SPA mode, not Start)
  • TanStack Query for server state
  • Tailwind CSS + Gambarino/Switzer from Fontshare
  • Puck for the canvas (drag, drop, resize, layout JSON)
  • Custom "describe-a-widget" modal → POST to Go

↕ JSON over HTTP — Vite dev server proxies /api/* to :8080

Where It Runs and How Someone Tries It

Two terminals, one browser

The Go backend listens on :8080; the Vite dev server runs on :5173 and proxies /api/* to the Go server. SQLite is a single file at backend/porchlight.db.

Environment: Go 1.22+, Node 20+, an OpenRouter key, a Brave Search key, in backend/.env. A .env.example is committed; .env is gitignored.

# Terminal 1 — backend cd backend go run . # Terminal 2 — frontend cd frontend npm install npm run dev # Then open http://localhost:5173

Submission: demo video (60-second screen recording of setup → drag-and-drop → describe-a-widget) and a public GitHub repo. Deployment is not required and not in scope.

Important Failure Modes

The two or three places this will actually break

  • OpenRouter fails or returns malformed JSON → kernel prompt shows inline "Try again"; no widget created. Go retries the parse once.
  • Brave Search returns no results → widget shows "Nothing new today — try refreshing later" instead of empty space.
  • Brave Search rate-limited (HTTP 429) → exponential backoff once, then surface the same "try again" treatment.
  • Session expired → any 401 triggers redirect to /login. The React fetch wrapper handles this.
  • LLM picks a data source we don't have → Go validates against the Registry; returns 422 and the prompt shows "Try again" with a hint.
  • LLM returns an unknown render archetype → frontend falls back to a generic card renderer.
  • API key missing at startup → Go fails fast with a clear console error.

What Was Simplified and Why

  • One OpenRouter model at a time, env-configurable. No per-widget model selection, no fallback chain. v1 ships one model; swap via env var.
  • No email sending for invites. Admin sees the invite link in the sidebar and copies it manually. Email is a real cost; out of scope for the PoC.
  • No password reset. Out of scope; re-invite if needed.
  • No caching of pre-built widget results. Articles and Events recomputed on every page load. v1 cares about correctness over efficiency.
  • No HTTPS, no production deployment. Local PoC, plain HTTP on :8080.
  • No multi-tenant concerns. Every user belongs to one family in v1.
  • "Free-form" render spec is constrained free-form. LLM picks from 5 archetypes (list, cards, hero, key_value, table); content is free. Truly open JSON is research-grade.
  • No JSON Schema validation of LLM output. We trust the system prompt + JSON-mode. Adding a schema validator is one line; doing it well is more.
  • Drag-and-drop is Puck's, not custom. Fully delegated to Puck. No custom DnD code.
  • No rate limiting. Local PoC, one family.

Decisions and Open Issues

  • Single-binary split architecture: Go API + React SPA. Learner preference; matches the React/TanStack/Puck stack they want to use.
  • OpenRouter via sashabaranov/go-openai. Most-used Go OpenAI client; OpenRouter is OpenAI-compatible. (Original suggestion: gollm; not chosen because of maintenance/API parity uncertainty.)
  • Stdlib net/http for routing. Most idiomatic for learning Go; zero deps.
  • alexedwards/scs/v2 for sessions. Server-side, SQLite-backed, httpOnly cookies.
  • modernc.org/sqlite for the driver. Pure Go, no CGO.
  • Puck for the canvas. Learner preference; drag, drop, resize, layout JSON all in.
  • TanStack Router in SPA mode, not TanStack Start. Start would overlap with the Go API.
  • Constrained free-form render spec. LLM picks from 5 archetypes; content is free. See Simplifications for the call against truly open.
  • OpenRouter model is configurable via OPENROUTER_MODEL env var. Default TBD; user picks.
  • One genuine learner uncertainty surfaced: the Go LLM integration path. Resolved: sashabaranov/go-openai pointed at OpenRouter. To verify during build: the chosen OpenRouter model supports JSON-mode for the kernel prompt. Most free models do; sanity-check on first kernel run.
